확정 요구사항

QAS 01
5배평상시 대비 동시 사용자
평균 3초보험료 산출 결과 표시
평균 60초가입 접수번호 표시

시스템이 정상 운영 중 이벤트 마감으로 동시 사용자 수가 평상시 대비 5배로 증가하고, 해당 부하가 5분에서 1시간 동안 지속되는 상황에서 고객이 보험료 산출 또는 보험 가입 접수를 요청하면, 시스템은 정확한 보험료 산출 결과를 평균 3초 이내에 제공하고 가입 접수번호를 평균 1분 이내에 발급하여 사용자 화면에 표시해야 한다.

측정 범위와 공통 설계 조건
  • 시간은 사용자 화면의 요청부터 결과 표시까지 측정한다.
  • 접수 완료 범위는 계약·결제 완료가 아닌 접수번호 발급이다.
  • 정확한 보험료 계산과 접수 내용·번호의 영속 저장을 유지한다. 실패·시간초과도 함께 계측한다.

Style·Pattern·Tactics 통합 전략

3 ALTERNATIVES

같은 QAS를 달성하기 위한 세 가지 대안이다. 각 전략의 구조와 동작을 먼저 살펴본 뒤 장단점과 Trade-off를 비교한다.

P1

계층형 모듈 구조의 복제 확장과 버전별 캐시

선택 전략

채널·업무·데이터 접근을 계층으로 구분하고 견적과 가입 접수의 업무 경계를 한 애플리케이션 안에서 유지한다. 동일 애플리케이션의 무상태 인스턴스를 늘려 이벤트 요청을 분산한다. 반복 사용하는 상품·요율 자료는 Cache-Aside로 조회한다. 보험료는 유효한 입력과 동일한 적용 버전으로 계산하며 가입 접수는 접수번호와 본문을 영속 저장한 뒤 응답한다. 이 통합 전략은 캐시로 반복 조회 비용을 줄이고 복제 인스턴스로 동시 처리 자원을 확보한다.

P1의 Style, Pattern, Tactics
StyleModule의 Layers·분해 스타일 + C&C의 Call-and-Return·Repository 스타일. 모듈형 모놀리스의 동일 배포 단위를 복제하는 적용안이다.
PatternCache-Aside. 상품·요율 기준정보의 캐시 조회와 미적재 시 원본 조회를 결합한다.
Tactics자원 증가·요청 분산, 이벤트 전 용량 확보, 반복 계산·조회 감소, 캐시 적용 버전 구분·무효화, DB 연결과 외부 호출량 제한. 전술 이름은 기존 조사 내용을 행동으로 정리한 것이며 SAIP 전술 목록의 직접 인용이 아니다.
동작
고객 요청 → 분산 진입점 → 무상태 업무 인스턴스 → 캐시/원본 → 계산 결과 또는 영속 접수 결과 표시.
QAS 연결
5배 동시 사용자 부하를 여러 인스턴스가 처리하고 반복 조회를 줄인다. 견적 평균 3초와 접수번호 표시 평균 60초는 사용자 화면 구간으로 각각 검증한다.
적용 한계
캐시 적중률이 낮거나 DB·외부 연계가 병목이면 확장 효과가 제한된다. TTL만으로 정확성을 보장하지 않으며 요율 개정과 버전 혼용을 시험한다.

P2

동기 견적·영속 접수와 비동기 후속 처리의 분리

보험료 결과와 가입 접수번호를 반환하는 짧은 경로를 후속 처리 경로에서 분리한다. 견적은 동기 산출 경로로 정확한 결과를 반환하고 가입 접수는 필요한 검증을 수행한 다음 접수 내용·번호·후속 처리 의도를 함께 저장한다. 이후 작업은 큐와 작업자가 처리한다. Half-Sync/Half-Async의 목적에 맞춰 동기·비동기 처리를 분리하고 큐 기반 부하 평탄화와 연결한다. 이렇게 후속 심사·연계의 지연이 접수번호 발급을 직접 막는 범위를 줄인다.

P2의 Style, Pattern, Tactics
StyleC&C의 Call-and-Return + Event 기반 스타일 + Repository 스타일. 사용자 응답 경로와 후속 이벤트 경로를 구분한다.
PatternHalf-Sync/Half-Async의 동기·비동기 분리 목적 + Queue-Based Load Leveling + Transactional Outbox. POSA의 상세 구현을 그대로 채택한 것으로 주장하지 않는다.
Tactics불필요한 응답 경로 작업 제거, 요청 버퍼링, 작업자 처리율 제어, 중복 방지·멱등 처리, 재시도 상한·백오프·지터, 대기열 연령 관측.
동작
견적 요청은 동기 산출. 가입 요청은 접수·outbox 원자적 저장 후 접수번호 응답. outbox → 큐 → 작업자 순서로 후속 처리.
QAS 연결
접수 완료 범위가 계약·결제 완료가 아닌 접수번호 발급이라는 확정 조건을 활용한다. 견적 3초는 별도 동기 경로를 최적화하고 접수 60초에는 검증·저장·화면 표시 시간을 포함한다.
적용 한계
필수 선행 검증을 임의로 뒤로 미루지 않는다. 큐 적재 성공만으로 업무 접수 성공을 대신하지 않는다. 생산량이 소비량을 계속 초과하면 후속 지연이 쌓이므로 1시간 부하와 복구 후 적체 해소를 시험한다.

P3

견적·접수 서비스 분리와 CQRS 기반 개별 최적화

견적과 가입 접수를 별도 실행 서비스로 나누어 이벤트 때 필요한 서비스의 자원을 각각 늘린다. 견적 서비스는 읽기·계산 모델을, 가입 접수 서비스는 검증·번호 발급·저장이라는 쓰기 모델을 중심으로 설계한다. CQRS로 조회와 명령의 책임을 나누고 동기 호출과 후속 이벤트를 조합한다. 두 서비스가 동일한 자원을 경쟁하는 범위를 줄이는 대신 서비스 간 통신·버전·데이터 일관성을 명시적으로 관리한다.

P3의 Style, Pattern, Tactics
StyleMicroservices 스타일 + C&C의 Call-and-Return·Event·Repository 스타일. 서비스 책임과 독립 확장 단위를 일치시킨다.
PatternCQRS + 선별적 Cache-Aside. CQRS의 읽기·쓰기 모델 분리를 적용하며 별도 DB와 Event Sourcing은 필수로 도입하지 않는다.
Tactics서비스별 자원 증가, 읽기·쓰기 경로별 자원 경쟁 제어, 유효 버전 캐싱, 타임아웃·재시도 예산, 개별 지연·오류·DB 부하 관측.
동작
분산 진입점 → 견적 조회·계산 서비스 / 가입 접수 명령 서비스 → 각 책임에 맞는 모델 → 공통 내구성 경계.
QAS 연결
견적 요청이 집중되면 계산 경로를, 가입 요청이 집중되면 접수 경로를 개별 확장한다. 조회 사본의 최신성이 입증되지 않으면 정확한 보험료 산출에 사용하지 않는다.
적용 한계
별도 읽기 저장소를 선택하면 동기화 지연과 read-after-write를 검증한다. 분산 운영·통합 시험 부담이 늘어난다.

전략별 장단점

PROS & CONS

P1 계층형 모듈 구조의 복제 확장과 버전별 캐시

장점. 반복 조회를 줄이고 동시 요청을 분산한다. 기존 모듈 구조를 유지해 변경 범위가 비교적 작다.

단점. DB·외부 연계가 병목이면 증설 효과가 제한된다. 캐시 버전 관리가 잘못되면 보험료 정확성에 영향을 준다.

P2 동기 견적·영속 접수와 비동기 후속 처리의 분리

장점. 후속 처리 지연을 접수번호 발급 경로에서 분리한다. 큐로 급증 부하를 완충하고 저장한 작업을 재처리할 수 있다.

단점. 큐·outbox·중복 방지·실패 처리가 추가된다. 견적 산출 자체의 속도는 별도로 개선해야 한다.

P3 견적·접수 서비스 분리와 CQRS 기반 개별 최적화

장점. 견적과 접수를 각각 확장하고 읽기·쓰기 경로를 개별 최적화한다.

단점. 서비스 통신·배포·통합 시험이 복잡해진다. 별도 조회 저장소를 쓰면 데이터 최신성도 관리해야 한다.

P1은 구조 변경을 줄이고, P2는 접수 응답과 후속 작업을 분리한다. P3는 업무별 독립 확장에 유리하지만 분산 운영 부담이 커진다.

기호를 단순 합산하지 않고 요구 충족 가능성과 구현·운영 부담을 함께 판단했다. 보안의 ‘-’는 보호할 API·저장소·권한이 늘어난다는 의미다.

선택 전략 · P1

계층형 모듈 구조의 복제 확장과 버전별 캐시

견적과 접수의 공통 처리 기반을 개선하면서 서비스·메시징 구조의 변경을 줄일 수 있다. 개발비 10억 원 제약과 현재 확보된 자료를 고려하면 우선 적용하기 적절하다.

받아들이는 Trade-off

P2의 후속 작업 분리나 P3의 서비스별 독립 확장 대신, 기존 모듈 구조 안에서 반복 조회와 동시 처리 병목을 먼저 개선한다.

보완점·개선점

상품·요율 캐시의 적용 버전을 계산 입력과 일치시키고 요율 개정 시 캐시를 갱신한다. 견적과 접수 경로의 DB 조회 및 외부 호출 비용을 줄인다.
