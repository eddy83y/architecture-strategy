QAS 02 / 신뢰성 · 가용성

가용성

배포와 점검 중에도 전체 업무의 트랜잭션과 임시 저장 데이터를 지킨다.

검토 결과 A2애플리케이션·인프라·DB 변경을 검증과 복귀 절차로 묶는다.↓

확정 요구사항

QAS 02
24시간서비스 운영 기준
99.9% 이상월간 서비스 가용률
중단 0유지보수 중 목표

시스템은 24시간 운영되며, 애플리케이션 배포·DB 변경·인프라 점검·외부 시스템 점검 중에도 전체 업무의 서비스를 지속해야 한다. 정상 여부는 접속 가능 여부뿐 아니라 업무 트랜잭션 처리까지 기준으로 판단한다. 유지보수 중 서비스 중단은 없어야 하며 월간 서비스 가용률은 99.9% 이상이어야 한다. 기능 축소는 허용하며, 화면 전환 시 임시 저장된 데이터까지 보존한다.

측정 범위와 공통 설계 조건
  • 정상 여부는 접속 성공이 아닌 업무 트랜잭션 처리까지 확인한다.
  • 실행 요소와 공통 의존성을 다중화하고, 점검 대상을 제외한 상태에서도 필요한 용량을 유지한다.
  • 구·신 버전과 DB 변경의 호환성, 진행 요청 배출, 임시 데이터 영속화를 함께 설계한다.
  • 외부 연계에는 대체 경로나 허용된 요청 보류가 필요하다.

Style·Pattern·Tactics 통합 전략

3 ALTERNATIVES

같은 QAS를 달성하기 위한 세 가지 대안이다. 각 전략의 구조와 동작을 먼저 살펴본 뒤 장단점과 Trade-off를 비교한다.

A1

다중 인스턴스와 카나리 배포를 통한 변경 위험 제한

계층형 업무 애플리케이션을 여러 인스턴스에서 운영하고 새 버전은 일부 실제 트래픽으로 먼저 검증한 뒤 점차 확대한다. 구·신 버전이 공존하는 동안 공통 저장 데이터와 인터페이스의 호환성을 유지하고 거래 오류나 지연이 악화되면 기존 버전으로 돌린다. 점검할 인스턴스를 제외해도 남은 인스턴스가 거래를 처리하도록 구성한다. 임시 저장은 특정 서버 메모리에서 분리한다. 카나리 관측과 복제 실행 구조를 함께 사용하는 가용성 전략이다.

A1의 Style, Pattern, Tactics
StyleModule의 Layers·분해 스타일 + C&C의 Call-and-Return·Repository 스타일. 모듈형 애플리케이션의 복제 실행 구조를 적용한다.
PatternCanary Deployment + 공통 상태 저장. 후자는 조사된 임시 저장 요구를 실행 구조에 적용한 설계 조합이며 새 패턴명으로 분류하지 않는다.
Tactics실행 요소 다중화, 준비 상태 확인, 진행 요청 배출, 구·신 버전 호환, 거래 지표 기반 관측·복귀, 임시 데이터 영속화.
동작
업무 트래픽 → 기존/카나리 인스턴스 → 공통 업무·임시 저장소. 업무 관측 결과로 카나리 확대 또는 기존 버전 복귀.
QAS 연결
애플리케이션 배포·호스트 점검 중 거래를 이어가며 잘못된 변경의 노출 범위를 줄인다. DB·외부 점검에는 아래 가용성 공통 조건을 함께 적용한다.
적용 한계
표본이 적거나 관측 시간이 짧으면 안전한 확대 판단이 어렵다. 공통 DB·인증·네트워크의 단일 장애점은 별도 제거해야 한다. 호환되지 않는 DB 변경을 카나리만으로 무중단 처리할 수 없다.

A2

Blue-Green 전환과 호환 가능한 DB 변경의 결합

선택 전략

운영 버전 Blue와 다음 버전 Green을 별도 실행 환경으로 준비한다. Green의 거래 처리를 검증한 후 진입 트래픽을 전환하고 문제가 발생하면 호환성이 유지되는 동안 Blue로 복귀한다. DB는 애플리케이션 환경 전환과 분리해 추가 변경·데이터 이행·코드 전환·구조 정리 순으로 변경한다. 두 환경이 진행 중 업무와 임시 저장을 이어 사용할 수 있게 해 실행 환경 교체와 데이터 구조 변경을 함께 다룬다.

A2의 Style, Pattern, Tactics
StyleC&C의 Call-and-Return·Repository 스타일 + Module의 Layers 스타일. Blue/Green은 스타일이 아닌 배포 패턴이며 두 환경이 업무 상태를 공유한다.
PatternBlue-Green Deployment + 조사된 추가→전환→삭제 방식의 호환 스키마 변경. 롤백 가능한 구간을 명시한다.
Tactics새 환경 사전 검증, 트래픽 전환, 진행 요청 배출, 인터페이스·스키마 호환, 단계적 데이터 이행·대조, 임시 저장 보존, 실패 시 복귀.
동작
Blue 운영 → Green 사전 검증 → 트래픽 전환. 공통 DB는 추가·이행 후 전환하며 구버전 제거 후에만 불필요 구조 삭제.
QAS 연결
애플리케이션·인프라 교체와 DB 변경의 상호 의존을 관리한다. 점검 중에도 동일한 업무 거래를 수행하는 것이 성공 기준이다. 외부 점검에는 가용성 공통 조건을 적용한다.
적용 한계
배포 때 추가 자원이 필요하며 공통 DB의 엔진 점검·잠금까지 자동 해결하지 않는다. 구버전에서 필요한 필드를 제거한 뒤에는 단순 트래픽 복귀가 불가능할 수 있다.

A3

외부 연계 격리와 영속 접수 기반 축소 운영

외부 연계를 업무 서비스와 분리하고 장애·점검 중인 연계는 회로 차단과 타임아웃으로 격리한다. 처리 보류가 허용되는 요청은 내부 저장소에 접수한 뒤 큐에 남겨 외부 복구 후 재처리한다. 다른 업무 서비스는 자체 거래를 계속 처리한다. 서비스 분리·이벤트 전달·장애 격리를 결합해 외부 점검의 파급을 줄이는 전략이다. 정확한 보험료 산출이나 실제 지급 완료에 필수인 외부 결과를 임의로 대체하지 않는다.

A3의 Style, Pattern, Tactics
StyleMicroservices + C&C의 Event·Call-and-Return·Repository 스타일. 내부 거래와 외부 연계 실행의 경계를 구분한다.
PatternCircuit Breaker + Queue-Based Load Leveling + Transactional Outbox. 영속 접수와 재전달을 연결한다.
Tactics장애 연계 격리, 대기시간 제한, 기능 축소, 요청 영속 보존, 제한된 재시도·백오프·지터, 멱등 처리·결과 대사, 업무별 정상 여부 관측.
동작
내부 업무 접수 → 업무·outbox 저장 → 큐 → 연계 어댑터 → 외부 시스템. 외부 점검 중에는 허용된 요청을 보류하고 복구 후 처리.
QAS 연결
외부 점검 중 접수 가능한 업무를 지속하면서 연계 장애가 다른 업무의 자원을 고갈시키지 않도록 한다. 내부 배포·DB·인프라 점검에는 가용성 공통 조건을 적용한다.
적용 한계
회로 차단은 외부 업무 결과를 생성하지 않는다. 보류가 허용되지 않는 필수 거래는 유효한 대체 연계가 있어야 한다. 오류 안내나 큐 적재만을 전체 업무의 정상 완료로 계산하지 않는다.

전략별 장단점

PROS & CONS

A1 다중 인스턴스와 카나리 배포를 통한 변경 위험 제한

장점. 일부 트래픽으로 변경을 검증해 장애 노출 범위를 제한한다. 기존 버전을 유지하면서 단계적으로 배포할 수 있다.

단점. 대표성 있는 트래픽과 관측 시간이 필요하다. DB 변경·외부 시스템 점검은 별도 대응이 필요하다.

A2 Blue-Green 전환과 호환 가능한 DB 변경의 결합

장점. 새 환경을 사전 검증하고 트래픽을 전환한다. 애플리케이션과 DB 변경의 호환성을 함께 관리하며 복귀 경로를 확보한다.

단점. 배포 시 추가 환경과 자원이 필요하다. 파괴적인 스키마 변경 이후에는 단순 복귀가 어려울 수 있다.

A3 외부 연계 격리와 영속 접수 기반 축소 운영

장점. 외부 점검의 영향을 다른 업무와 분리한다. 보류 가능한 요청을 저장하고 외부 복구 후 처리한다.

단점. 외부 결과가 필수인 거래는 대체 경로가 필요하다. 보류 상태·재처리·결과 대사 관리가 복잡해진다.

A3의 성능 이점은 장애 연계가 정상 업무의 자원을 오래 점유하는 상황을 줄이는 효과다. 외부 거래의 완료가 빨라진다는 뜻은 아니다.

기호를 단순 합산하지 않고 요구 충족 가능성과 구현·운영 부담을 함께 판단했다. 보안의 ‘-’는 보호할 API·저장소·권한이 늘어난다는 의미다.

선택 전략 · A2

Blue-Green 전환과 호환 가능한 DB 변경의 결합

QAS에 포함된 애플리케이션 배포·인프라 교체·DB 변경을 함께 다루고, 검증과 복귀 절차를 명확히 구성할 수 있다. 추가 환경을 운영하는 부담을 받아들이는 대신 변경 중 서비스 지속에 집중하는 선택이다.

받아들이는 Trade-off

A1의 점진적 노출이나 A3의 외부 장애 격리보다, 새 환경의 사전 검증과 전환·복귀 경로를 우선한다. 배포 시 추가 자원과 DB 호환성 관리가 필요하다.

보완점·개선점

외부 시스템 점검에는 유효한 대체 연계를 함께 구성한다. 구·신 버전의 DB 호환성과 공통 임시 저장을 유지해 환경 전환 중에도 업무를 이어간다.
